# 🏠 airdnd

> **2025 코드스쿼드 마스터즈 백엔드 팀 프로젝트** 의 일환으로 Airbnb와 같이 숙소 예약을 중개하는 서비스입니다.
> 
> 이 저장소는 팀 원본 저장소를 **fork**한 개인 사본으로, 제가 담당한 **예약 도메인**을 중심으로 정리한 문서입니다.

<br>

## 🔧 트러블슈팅 — 예약 동시성 & 정합성

### 문제
멀티 인스턴스 환경에서 **동일 숙소·동일 날짜에 여러 유저가 동시에 예약**을 시도할 때 중복 예약이 발생했습니다.

### 1. 동시성 제어 — Redis 분산락 도입

| 방식 | 검토 결과 |
|---|---|
| `synchronized` | 인스턴스 간 메모리를 공유하지 못해 **멀티 인스턴스 환경에서 사용 불가** |
| DB 비관적 락 | 멀티 인스턴스 환경에서 동작하지만 **락 보유 동안 커넥션을 점유** → 트래픽 급증 시 커넥션 풀 고갈 |
| DB 낙관적 락 | 커넥션을 점유하진 않지만, **경합이 잦으면 재시도가 증가** -> 응답속도, 처리량 문제 발생 |
| **Redis 분산락** | 인스턴스와 무관하게 동작하며 **DB 커넥션을 점유하지 않음** |

→ 숙소 ID + 예약 날짜별로 락을 걸고, `MultiLock`을 통해 락을 원자적으로 획득하여 동시성 제어

### 2. 정합성 문제 — 트랜잭션 경계 분리

분산락을 도입했음에도 중복 예약이 발생했습니다.

- **원인**: 락이 **트랜잭션 커밋 전에 해제**되고 있었습니다. 그 배경에는 **동일 클래스 내부 호출로 `@Transactional` 프록시가 적용되지 않는 문제**가 있었습니다.
- **해결**: 락 로직을 **별도 객체로 분리**해 프록시를 거치게 함으로써, **커밋 완료 후 락이 해제되도록** 순서를 보장했습니다.

### 3. 한계점 및 개선점 적용

분산락은 **Redis 장애나 leaseTime 만료 시 무력화**될 수 있습니다. 즉 분산락은 정합성을 보장하는 장치가 아니라 **충돌 빈도를 줄이는 최적화**에 가깝다고 판단했습니다.

→ 정합성의 최종 보장을 **DB UNIQUE 제약**에 위임하고, **락을 우회한 동시 요청 테스트**로 DB가 최종적으로 정합성을 보장함을 검증했습니다.

## testcontainers 도입을 통한 테스트 신뢰성 확보

로컬 환경에서 사용하는 H2 DB는 배포 환경에서 사용하는 MySQL과 **SQL 문법뿐 아니라 DB 동작 방식**이 달라 동시성 검증 결과를 신뢰하기 어렵다고 판단해 **testcontainers**로 배포 환경과 동일한 **MySQL · Redis 환경**에서 테스트하여 동시성을 검증했습니다.

- **100개 스레드 동시 예약** → 먼저 락을 획득한 **1건만 저장** 확인
- **락을 우회한 동시 요청** → **DB UNIQUE 제약이 최종적으로 중복 예약을 차단** 확인

<br>

## flyway를 통한 DB 스키마 관리 

DDL을 수동 적용하면 **환경 간 스키마가 불일치 하게 되는 상황이 발생하고, 변경 이력을 추적할 수 없어**, 스키마 변경을 flyway의 마이그레이션 파일을 통해 버전 관리하고 **배포 시 자동 적용**되도록 구성했습니다.
